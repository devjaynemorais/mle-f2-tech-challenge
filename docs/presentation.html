Um recomendador que aprendeu a distinguir
"visto" de "comprado".

Sistema de recomendação Top-K para e-commerce sobre o dataset RetailRocket — da tarefa mal formulada (AUC≈0,5) até um NCF multi-task validado em dados reais, com pipeline reprodutível em DVC + MLflow. Este material documenta cada decisão para você apresentar e defender.

00 — Leia isto primeiro

Resumo em 1 minuto

Construímos um sistema que, pra cada cliente de uma loja virtual, decide quais produtos mostrar sem que ele precise buscar nada — tipo a seção "recomendado pra você". A primeira versão não funcionava de verdade: ela "decorava" os dados de um jeito que parecia bom no papel, mas não ajudaria ninguém na prática. Reformulamos a tarefa do zero, comparamos sempre contra o concorrente mais óbvio (só mostrar os produtos mais vendidos), e só consideramos "bom" o que realmente supera esse concorrente. No fim, o modelo supera a estratégia de "mais vendidos" tanto pra prever compra quanto pra prever navegação — exceto para clientes totalmente novos, onde nada substitui ter algum histórico, e por isso a estratégia simples continua cobrindo esse caso.

Glossário — os termos que aparecem no resto do material

Ranking
Ordenar uma lista de produtos do mais pro menos relevante pra uma pessoa — diferente de "classificação", que só responde sim/não pra um produto isolado.
Baseline de popularidade
O concorrente mais simples possível: recomendar sempre os produtos mais vistos/vendidos, sem personalizar nada. É a barra mínima que qualquer modelo precisa superar pra justificar o investimento em ML. É um baseline de ranking — compete em "qual lista ordenar melhor".
Baseline de classificação (dummy / logistic)
Adversário fraco de um jogo diferente: "esse par usuário-item é positivo ou não?" (sim/não), não "que lista ordenar". dummy chuta sempre a classe majoritária; logistic é uma regressão logística de verdade. Fácil de confundir com o baseline de popularidade acima — são baselines de tarefas diferentes, ver seção 06.
Embedding
Um "resumo numérico" que o modelo aprende pra representar cada usuário, produto ou categoria. Usuários com gosto parecido, ou produtos parecidos, acabam com resumos numéricos parecidos.
Cold-start
Quando o modelo encontra um usuário ou produto que nunca viu antes — sem histórico, não tem o que aprender sobre preferência.
Warm / cold (usuário)
Warm = usuário que já apareceu nos dados de treino. Cold = usuário novo, que só aparece depois — é o caso de cold-start acima.
NDCG@K
Nota de 0 a 1 pra qualidade de uma lista Top-K: premia colocar os produtos certos bem no topo, não só em algum lugar da lista.
Recall / Precision / HitRate@K
Outras notas de 0 a 1 pra mesma ideia. Recall: quanto do que era relevante a lista encontrou. Precision: quanto da lista é relevante. HitRate: acertou pelo menos um item, sim ou não.
AUC (ROC-AUC)
Mede se o modelo separa bem "vai interagir" de "não vai interagir" — não mede se a ordem final da lista é boa (por isso não é a métrica principal aqui).
Vazamento temporal
Quando o modelo "aprende" usando informação que só existiria no futuro — infla os números na hora do teste sem refletir a realidade.
Negative sampling
Mostrar pro modelo, de propósito, exemplos de "isso o usuário não quis" (produtos nunca vistos por ele) — sem isso ele nunca aprende o que rejeitar.
Multi-task
Treinar o mesmo modelo pra prever duas coisas ao mesmo tempo (aqui: "vai comprar" e "vai só olhar"), compartilhando o que ele aprendeu entre as duas.
01 — Contexto

O problema de negócio

Uma loja virtual precisa decidir, para cada usuário, quais produtos mostrar quando não há uma busca explícita — na home, no "quem viu também viu", no e-mail de retenção. Isso é um problema de ranking, não de classificação: o que importa não é "esse usuário vai comprar esse item?" isoladamente, é "destes milhares de itens, quais N eu coloco no topo?".

Por que não é trivial

O catálogo é grande, o histórico por usuário é curto (mediana de ~2 interações) e a maioria dos eventos é navegação sem intenção de compra. Um recomendador ingênuo aprende a prever popularidade, não preferência — e um bom recomendador precisa superar esse baseline, não apenas "funcionar".

Por que isso importa aqui

O Tech Challenge avalia o pipeline de ponta a ponta — não só a métrica final. Pipeline de dados versionado (DVC), rastreamento de experimentos (MLflow), reprodutibilidade e comparação honesta contra baseline valem tanto quanto o modelo em si.

02 — Dados

RetailRocket E-commerce Dataset

Logs reais e anonimizados de uma loja virtual: eventos de navegação, carrinho e compra ao longo de 4,5 meses (mai–out 2015), publicados no Kaggle.

Distribuição de eventos

  • 882K view (navegação)
  • 48K addtocart
  • 18K transaction

Funil: view → addtocart converte ~4–5%; addtocart → transaction converte ~35–45%. A imensa maioria do sinal disponível é navegação, não compra.

Por que isso molda todo o design

Com mediana de ~2 interações por usuário (base bruta) e catálogo de ~235K itens, qualquer feature agregada por usuário é rala. Isso empurra o design pra: (a) features causais que dão sinal por linha, não só por entidade, e (b) um baseline de popularidade forte o bastante pra ser um adversário de verdade, não um palha.

Por que filtrar usuários com menos de 5 interações

A distribuição de interações por usuário segue power-law (poucos usuários concentram a maioria dos eventos; mediana bruta ≈ 2 interações/usuário) — é o único filtro de linha aplicado no pipeline (RetailRocketPreprocessor._filter_users(), estágio preprocess), antes de qualquer split ou feature. Nenhum evento é descartado por tipo: view, addtocart e transaction passam todos — o que muda é o papel de cada um (seção 04).

Corte% de usuáriosEfeito
≥5 interações (mantidos)~20–25%preservam ~70%+ dos eventos brutos
<5 interações (descartados)~75–80%visita única/passagem — sem histórico suficiente pra features causais informativas

É uma troca deliberada: perder ~75% dos usuários custa pouco volume de eventos de treino, porque quem tem menos de 5 interações raramente gera sinal de preferência aprendível (nem frequency nem engagement_score diferenciam nada com 1–2 pontos). Threshold documentado em docs/eda.md#decisões-para-o-pré-processamento.

03 — Onde começou

O diagnóstico: por que o primeiro modelo tinha AUC≈0,5

Antes da spec 001-recommender-quality, o pipeline treinava e media o modelo de um jeito que garantia que ele não aprendesse nada de útil — não por um bug de código, mas por uma formulação de tarefa incompatível com o problema real. Cinco causas, todas na mesma raiz:

🔎
Em termos simples Era como mostrar pro modelo a mesma pergunta duas vezes e dar respostas diferentes, sem nenhuma pista de por quê. Ele não tinha como adivinhar o padrão certo — o problema não era o modelo ser "ruim", era a prova estar mal formulada.
  1. Rótulo sobre o próprio evento. O label era weight >= 3 calculado em cima do tipo de evento daquela mesma linha — mas nenhuma feature codificava esse tipo de evento. Duas linhas do mesmo usuário ficavam com vetor de features quase idêntico e rótulos opostos: o modelo via a mesma entrada gerar respostas diferentes e não tinha como separar as classes.
  2. Vazamento temporal nas agregações. Frequência, engajamento e recência eram calculados sobre o dataset inteiro antes do split — uma linha de treino carregava informação de eventos que só aconteceriam no futuro (val/teste).
  3. Sem negative sampling. O modelo só via interações que aconteceram — nunca aprendeu o conceito de "não-interação". No serving, ele precisa pontuar itens que o usuário nunca viu: distribuição de entrada totalmente diferente da de treino.
  4. user_idx/item_idx como número cru. Os ids entravam direto no MLP como float, sem embedding — o design (documentado em três lugares diferentes do projeto) sempre previu nn.Embedding, mas a implementação nunca chegou lá.
  5. Métrica errada. Treino e avaliação usavam ROC-AUC/F1 sobre um threshold de peso, mas o produto real é ranking Top-K (HitRate/Precision/Recall/NDCG@K).
Lição estrutural: o problema nunca foi "o modelo é fraco" — foi "a tarefa como formulada não tinha solução aprendível". Consertar hiperparâmetro não resolveria nada disso.
04 — Fundação de dados

Features causais e definição de rótulo

Toda feature agregada é calculada as-of: cada linha enxerga só eventos estritamente anteriores a ela, por construção — independente de onde o split cronológico corta os dados. Isso elimina o vazamento por design, não por disciplina.

🔎
Em termos simples Pra ensinar o modelo, mostramos exemplos de "isso o usuário quis" (comprou ou colocou no carrinho) e "isso ele não quis" (produtos que ele nunca viu). As "features" são pistas sobre o comportamento de cada usuário e produto até aquele momento — nunca uma informação que só existiria depois.

Cada coluna do contrato responde a um achado específico do EDA (notebooks/01_exploratory_data_analysis.ipynb, consolidado em docs/feature_selection.md) — a lista não foi "usar tudo que existia no CSV":

O que foi descartado, e por quê: popularity_tier chegou a ser calculado numa versão anterior e foi removido deliberadamente — view_count contínuo e causal carrega a mesma informação sem discretizar. Sessionização (agrupar eventos por visita) e taxa de conversão por usuário foram cogitadas no EDA e ficaram de fora desta rodada (seção 11 — trabalho futuro).

Transformação antes de entrar no modelo

frequency, engagement_score e view_count têm cauda pesada (power-law) — sem tratamento, a maioria dos usuários/itens fica espremida perto de zero e a variância do z-score é dominada por poucos outliers muito populares. Por isso essas três colunas passam por log1p antes do StandardScaler (as demais contínuas só são escalonadas). O scaler é ajustado somente no treino e serializado dentro do model.pkl (D5, seção 05) — treino, avaliação e serving nunca reajustam ou reimplementam essa normalização.

Rótulo, pesos de evento e o papel de cada tipo de evento

Os três tipos de evento do RetailRocket entram todos no pipeline, mas cada um cumpre um papel diferente — nenhum é descartado, e nenhum é tratado como equivalente aos outros:

EventoPesoOnde entra
view1Sempre em engagement_score/view_count; não é rótulo positivo de treino; conta na relevância ampla de avaliação e alimenta a cabeça auxiliar view_head (multi-task, spec 002)
addtocart3Rótulo positivo (POSITIVE_EVENTS); conta nas relevâncias forte e ampla
transaction5Rótulo positivo; conta nas relevâncias forte e ampla; maior peso — menor volume, maior qualidade de sinal (EDA)

A hierarquia de pesos (1 / 3 / 5) reflete o funil de conversão medido no EDA (view→addtocart ~4–5%, addtocart→transaction ~35–45%): quanto mais raro e mais perto da compra, maior o peso. Por que view não é positivo de treino: é o evento mais barato e mais ambíguo — a maioria é navegação sem intenção de compra (seção 02); tratá-lo como positivo diluiria o sinal de preferência real com ruído. Ele só conta como "acerto" na avaliação de relevância ampla, que mede um objetivo diferente (engajamento geral, não conversão) — e, desde a spec 002, também vira alvo da cabeça auxiliar view_head (seção 05), que aprende esse sinal sem deixá-lo contaminar a cabeça principal.

Definição única de rótulo (src/data/labeling.py)

Positivo

Evento addtocart ou transaction — sinal forte de preferência. Única fonte da verdade no projeto; nenhum outro módulo redeclara threshold.

Negativo

Itens do catálogo de treino nunca vistos pelo usuário, amostrados uniformemente (não por popularidade) a 8:1 por positivo, com view_count/features de par recalculadas as-of o timestamp do positivo.

Os filtros da amostragem de negativos

  • Rejeição de vistos. Um candidato só vira negativo se não está no conjunto "visto" do usuário (histórico + split sendo rotulado) — até 20 rodadas de reamostragem (_MAX_RESAMPLE_ROUNDS) antes de descartar a linha, pra um positivo real nunca vazar como negativo.
  • Uniforme, não por popularidade. A escolha original foi popularidade^0,75 (estilo word2vec/NCF) — revertida depois de medir em dados reais que o modelo aprendia a punir itens populares e perdia pro próprio baseline de popularidade (NDCG@20 0,105 vs. 0,348; AUC teste 0,59 — research.md D1 e seção 09). O expoente segue parametrizado (labeling.popularity_alpha) pra eventual retuning, mas roda em 0 hoje.
  • Razão 8:1. Oito negativos por positivo — balanço empírico entre dar sinal suficiente de "o que rejeitar" e não afogar o gradiente dos ~66K positivos fortes por época.
  • Por que não full-softmax. O catálogo filtrado tem ~104K itens — pontuar todos por linha de treino é inviável nesta escala; negative sampling é o padrão da literatura de NCF/BPR pra este regime de esparsidade.

O sinal auxiliar de view (multi-task, spec 002)

Além dos positivos/negativos acima, uma fração dos eventos view reais do split é amostrada como sinal auxiliar (view_sample_ratio: 8 — mesma ordem de grandeza dos negativos) e recebe view_label=1, alimentando só a cabeça view_head. Por que não 100% dos views: a base tem ~882K views contra ~66K positivos fortes — usar tudo infla o dataset em ~13x e faz o gradiente do sinal auxiliar dominar o principal, exatamente o risco que a spec 002 antecipou e que a máscara de loss (seção 09) teve que corrigir depois de aparecer na prática.

05 — O modelo

NCF multi-task: duas cabeças, um trunk

Neural Collaborative Filtering com embeddings de usuário, item e categoria, mais uma camada extra que a maioria das implementações de referência não tem: duas cabeças de saída compartilhando a mesma representação latente.

🔎
Em termos simples O modelo aprende um "perfil resumido" (uma lista de números) pra cada usuário e cada produto, e usa esses perfis pra prever se um vai combinar com o outro. Ele dá duas opiniões separadas sobre o mesmo par: uma sobre "vai comprar de verdade" e outra sobre "vai só dar uma olhada" — as duas aprendem juntas, compartilhando a mesma base.

Três decisões de design que valem a pena defender

Índice "unknown" reservado

O último índice de cada tabela de embedding (não o 0, que já é um id real do factorize) recebe ids ausentes do treino. Treinado via unknown_dropout (10%): a cada época, uma fração dos ids conhecidos é roteada pra "unknown" de propósito, pra esse embedding aprender o "usuário/item médio" em vez de ficar com inicialização aleatória sem gradiente.

Categoria pelo id real, não pelo roteado

Bug real encontrado nesta sessão: a categoria era consultada depois de rotear o item pra "unknown", descartando sinal de conteúdo válido pra qualquer item ausente do treino. Corrigido pra consultar pelo item_idx real — o embedding do item continua "unknown" (não aprende identidade que nunca viu), só a categoria (sinal independente) deixa de ser jogada fora.

Duas cabeças, uma loss mascarada

strong_head prevê interação forte (cenário principal); view_head prevê visualização (relevância ampla). Compartilham o trunk, mas linhas de "visto e não comprado" são mascaradas da loss forte — só alimentam a view. Sem essa máscara, o modelo aprendia a tratar "visto" como "nunca visto" e regredia o cenário principal (seção 09).

Artefato auto-contido

model.pkl carrega a rede e o StandardScaler ajustado no treino e os vocabulários/máscaras — treino, avaliação e serving nunca reimplementam a normalização, eliminando risco de descasamento treino↔serving por construção.

MLflow: dois runs por execução completa

train abre um run ("ncf") logando hiperparâmetros + val_auc/val_ndcg_at_20 + o artefato. evaluate abre outro run ("evaluate") só pra logar as métricas de teste — não treina nada. promote não abre run nenhum: só lê os existentes.

Promoção não é "o mais recente"

find_best_model_run varre todo o histórico do experimento e promove o melhor por val_ndcg_at_20 — um retreino não substitui automaticamente o que já estava em produção se for pior. Isso quase causou um incidente real (seção 09).

Duas famílias de baseline — fácil de confundir

train.model_type aceita dummy, logistic ou ncf (src/models/baselines.py, via ModelFactory) — mas esses são baselines de classificação (chutar a classe majoritária / regressão logística), avaliados nas mesmas métricas de AUC/F1 do NCF. É um adversário diferente do baseline de popularidade (seção 07), que é de ranking. dvc repro só treina o model_type corrente do params.yaml (hoje ncf) — comparar os três exige rodar o estágio train três vezes.

Automação: make compare-baselines

scripts/compare_baselines.py treina+avalia dummy, logistic e ncf em sequência, restaura o params.yaml ao final mesmo se algo falhar no meio (try/finally) e promove uma única vez, deixando o Registry escolher o melhor por val_ndcg_at_20 entre todos os runs logados — seguro mesmo com os baselines fracos também no MLflow. Execução real desta sessão, validando o pipeline do zero:

Achado na primeira execução desta comparação: os três runs de treino apareciam todos com o mesmo nome na UI do MLflow (mlflow.run_name era um valor fixo, nunca incorporava o model_type; evaluate sempre logava como "evaluate") — impossível distinguir qual run era qual sem abrir cada um. Corrigido em trainer.py/evaluate.py para <run_name>-<model_type>, e reexecutado pra confirmar: os seis runs (train-dummy, evaluate-dummy, train-logistic, evaluate-logistic, train-ncf, evaluate-ncf) já aparecem distinguíveis na UI, com os mesmos números acima reproduzidos de ponta a ponta — segunda confirmação, com seed fixa, de que o pipeline é determinístico.

Serving

FastAPI (GET /recommend?user_id=&top_k=) carrega o modelo Production do Registry (com fallback pro artefato local se o MLflow estiver fora do ar) e um FeatureStore em memória. Usuário conhecido → pontuado pelo modelo entre os 5.000 itens mais populares não vistos. Usuário desconhecido, ou candidatos esgotados → fallback de popularidade. A API nunca retorna lista vazia.

07 — Metodologia

Protocolo de avaliação

A pergunta certa não é "o modelo classifica bem?" — é "o modelo rankeia melhor que só mostrar os mais populares?". Todo o protocolo foi desenhado em volta dessa pergunta.

🔎
Em termos simples Pra testar o modelo, montamos uma "prova" com as respostas certas escondidas entre 100 alternativas erradas, e vemos se ele consegue colocar as certas no topo da lista — sempre comparando contra "só mostrar os produtos mais vendidos", que é o concorrente mais óbvio e mais difícil de vencer numa base com tão pouco histórico por usuário.

Ranking Top-K por usuário (sampled)

  1. Para cada usuário de teste, junta todos os seus positivos + 100 negativos não vistos numa única lista de candidatos.
  2. O mesmo conjunto de candidatos (mesma semente) é pontuado pelo modelo e pelo baseline de popularidade — comparação justa, sem vantagem de dados.
  3. Calcula HitRate/Precision/Recall/NDCG @{10, 20} por usuário, agrega por média.

Duas definições de relevância

Forte: só addtocart/transaction — intenção real de compra, cenário principal. Ampla: inclui view (teto de 20 positivos/usuário) — mais próxima de "engajamento geral", tarefa em que popularidade é quase ótima por definição.

Dois segmentos de usuário

Warm: usuário com histórico no treino. Cold: usuário que só aparece em val/teste — zero sinal de embedding aprendido, só o fallback resolve.

Por que "sampled" e não catálogo inteiro

Rankear os ~104K itens do catálogo inteiro por usuário seria caro e, na esparsidade desta base, é o padrão da literatura (He et al., NCF) usar candidatos amostrados. Tem viés conhecido (Krichene & Rendle, 2020) — válido pra comparação interna consistente entre modelo e baseline, não como número absoluto.

Por que a métrica de promoção não é AUC

registry.metric: val_ndcg_at_20 — NDCG mede ranking, que é o produto de verdade. Além disso, desde a spec 002 o ROC-AUC de classificação ficou inflado por construção (ver caveat na seção 08): promover pelo AUC teria escolhido um modelo pelo motivo errado.

09 — A parte que mostra rigor

A regressão que quase virou produção

Esta é provavelmente a pergunta mais valiosa pra antecipar numa defesa: "vocês testaram em dados reais, ou só confiaram nos testes sintéticos?". A resposta é que testamos — e um erro real apareceu.

🔎
Em termos simples Numa primeira tentativa de ensinar o modelo a prever "navegação" além de "compra", sem querer pioramos a parte que já funcionava bem. Só descobrimos isso porque testamos com dados reais antes de colocar em produção — e corrigimos sem perder o que tinha dado certo antes.
  1. Sintoma. A primeira versão da loss combinada (strong_bce + λ·view_bce, aplicada a todas as linhas do batch) regrediu o cenário principal: NDCG@10 forte/warm caiu de 0,317 para 0,161 — enquanto a relevância ampla melhorava (0,207 → 0,332). Ganho em um lugar, perda maior em outro.
  2. Diagnóstico por ablation. Em vez de reverter tudo, isolei a variável: desliguei só o multi-task (view_sample_ratio: 0), mantendo as features de par. Resultado: o cenário principal não só voltou como melhorou (NDCG@10 0,341) — a causa estava especificamente na Frente B (multi-task), não na Frente A (features de par).
  3. Causa raiz. ~528 mil linhas de view amostradas (vistas mas não convertidas) entravam como negativo também na loss da cabeça forte. O modelo aprendia que "visto mas não comprado" era equivalente a "nunca visto" — distinção que o ranking do cenário principal penaliza duramente.
  4. Correção cirúrgica. Mascarar essas linhas (y_view=1 AND y=0) só da loss strong — elas continuam alimentando a loss view normalmente. Depois da correção, os dois cenários melhoraram juntos, sem trade-off.

Bônus: quase promovemos um modelo quebrado

Ao rodar dvc repro pela primeira vez com o contrato v3, o estágio promote escolheu um run antigo (contrato v2, de antes da spec 002) porque tinha uma métrica melhor que o modelo recém-treinado — find_best_model_run não filtra por compatibilidade de versão, só pela métrica. Esse modelo antigo, carregado com o código atual, quebrava (StandardScaler esperando 6 features, recebeu 8). Limpei 20 runs incompatíveis do MLflow antes de seguir.

Frase de defesa: "o processo de validação encontrou dois problemas reais — um de qualidade de modelo, um operacional — antes de qualquer um deles chegar em produção. É exatamente o que o pipeline deveria fazer."
10 — Honestidade

Limitações conhecidas

Documentar limitação não é fraqueza de projeto — é sinal de que a avaliação foi feita direito. Estas são reais e estão no model_card.md.

Cold-start real (zero-histórico)

Sem nenhuma interação prévia, não há o que um embedding aprenda — o modelo puro fica perto do aleatório (NDCG@10 0,072 vs. 0,307 da popularidade). Nem as features de par nem o fix de categoria resolvem isso; é estrutural. Mitigação: fallback de popularidade no serving, que é forte (NDCG@10 ≈ 0,31).

Métricas de classificação infladas

Desde o contrato v3, ROC-AUC/AP/F1 sobem por causa de como as features de par são construídas em relação aos negativos amostrados (ver seção 08) — não refletem qualidade de ranking na mesma proporção. Métricas de ranking são a referência.

Métricas de ranking são sampled

100 negativos por usuário, não o catálogo inteiro — viés conhecido (Krichene & Rendle, 2020). Válido pra comparação interna consistente, não como número absoluto de "qualidade real".

Sem modelagem de sessão

Nenhum sinal de sequência dentro de uma visita — cada evento é independente do anterior na arquitetura. Candidatos do serving vêm de um pool fixo (5.000 itens mais populares), não do catálogo inteiro.

12 — Preparação

Perguntas prováveis da banca

Q.Por que NDCG e não acurácia/AUC como métrica principal?

Porque o produto é uma lista ordenada de recomendações, não uma classificação binária isolada. NDCG penaliza acertos em posições baixas da lista — exatamente o que importa quando só os primeiros K itens aparecem pro usuário. E desde a spec 002, AUC ficou inflado por um artefato de construção das features (seção 08) — promover por ele escolheria o modelo errado.

Q.Como vocês garantem que não há vazamento temporal?

Duas camadas: (1) todas as agregações são causais/as-of por construção — cada linha só usa eventos estritamente anteriores; (2) um teste automatizado (test_no_temporal_leakage_features_unchanged_by_future) verifica isso truncando o dataset e conferindo que as features das primeiras linhas não mudam.

Q.O que acontece com um usuário totalmente novo?

Cai no fallback de popularidade no serving — a API nunca retorna lista vazia. É uma limitação honesta e documentada, não escondida: o modelo puro é perto do aleatório nesse segmento (seção 10), e não fingimos que não é.

Q.Qual foi o maior erro do projeto, e como perceberam?

Dois, cada um numa spec: negativos amostrados por popularidade^0,75 (spec 001) ensinaram o modelo a punir itens populares e ele perdeu pro próprio baseline (AUC 0,59). E a loss multi-task sem máscara (spec 002) regrediu o cenário principal mesmo corrigindo a relevância ampla. Os dois foram achados comparando contra o baseline de popularidade em dados reais — não em teste sintético.

Q.Por que popularidade como baseline, e não outro modelo?

Porque é o adversário que importa no mundo real: é barato, difícil de superar numa base tão esparsa, e é literalmente o que um sistema sem machine learning faria. Superar popularidade é a barra mínima de "isso vale o investimento em ML".

Q.O pipeline é reprodutível de verdade?

Sim — semente fixa (42) em split, labeling e treino; dvc repro reexecuta só estágios cujas dependências/parâmetros mudaram (rastreado por hash em dvc.lock); todo run fica registrado no MLflow com hiperparâmetros e métricas. Essa sessão validou isso rodando o pipeline do zero mais de uma vez sobre os mesmos dados.
